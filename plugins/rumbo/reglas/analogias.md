# Explicar con analogía

Regla compartida por todos los skills de `rumbo`. Quien usa estos skills trabaja en gestión: sabe de procesos, pedidos, expedientes y plazos, y no tiene por qué saber qué es un repo. Lo técnico se explica con algo de su día a día, la primera vez que aparece.

## Cómo

1. Antes de usar un concepto técnico en lo que le decís a la persona, mirá `ya_conoce` en `_rumbo.md` (forma en [`carpeta.md`](carpeta.md)). Si está ahí, usalo sin explicar.
2. Si no está, acompañalo de **una analogía cotidiana en una línea**, en el mismo mensaje, pegada al concepto. Tono de colega que explica al pasar: dato concreto, sin "es muy fácil", sin "no te preocupes", sin pedir disculpas por lo técnico.
3. Después de explicarlo, sumalo a `ya_conoce`. Si la persona dice que ya lo sabe, también se suma, y seguís sin explicarlo.
4. Si la persona pide más detalle, dáselo; la línea es el piso, no el techo.

Un concepto técnico es cualquier palabra que un administrativo no usaría en su oficina: herramienta, formato o mecanismo informático. Las palabras del método (índice, mapa, ticket, plano) se explican igual la primera vez.

## Analogías de partida

Sirven de punto de partida; si la persona trae una imagen propia de su trabajo, usá la suya.

| Concepto | Analogía |
|---|---|
| carpeta de contexto | el bibliorato con índice que le dejás a tu reemplazo para que siga sin llamarte |
| índice (`CLAUDE.md`) | la carátula del bibliorato: dice qué hay adentro y en qué solapa |
| skill | un instructivo escrito que el asistente sigue paso a paso cuando lo llamás por su nombre |
| plugin | una caja de instructivos que se instala de una vez y trae varios skills |
| CLAUDE.md de usuario | el reglamento interno: las instrucciones que tu asistente lee siempre, en cualquier carpeta |
| ticket | un pedido en la mesa de entradas: una pregunta, con número, que se cierra cuando tiene respuesta |
| mapa | la hoja de ruta de un trámite largo: qué ya se resolvió y qué falta |
| plano | el pliego que le pasás a otro para que haga el trabajo sin tener que preguntarte |
| frente | la bandeja de lo que se puede despachar hoy: lo que no espera la firma de nadie |
| niebla | lo que sabés que va a venir en el trámite pero todavía no se puede pedir con precisión |
| maqueta | la maqueta del arquitecto: de cartón, para ver si la idea cierra antes de construir |
| hallazgo | el informe de lo que averiguaste, con la fuente de cada dato, como un dictamen con sus citas |
| cuestionario | el formulario que le mandás a otra área para que te conteste lo que solo ella sabe |
| criterio de terminado | la lista de control de la recepción de una obra: cada punto se mira y es sí o no |
| HTML | una página como las de internet, guardada en un archivo que se abre con doble clic |
| CSV | una planilla en texto común: cada renglón una fila, las columnas separadas por punto y coma |
| Markdown | texto común con algunas marcas (`#` para títulos, `-` para listas) que se lee igual con o sin programa |
| git | un sistema que saca una foto fechada de toda la carpeta cada vez que se lo pedís |
| commit | una de esas fotos, con una nota de qué cambió, como el sello de "recibido" con fecha |
| repo | el expediente completo con todas sus fotos, desde la primera |
| GitHub | el archivo central en internet donde se guarda una copia del expediente |
| push | mandar las fotos nuevas al archivo central |
| repo privado | expediente reservado: lo ven solo las personas que vos autorizás |
| issue | el ticket, pero cargado en GitHub en vez de en un archivo de la carpeta |
| `.env` | el sobre cerrado con claves que queda en tu cajón y nunca va al archivo central |
| `.gitignore` | la lista de lo que no sale de la oficina aunque se manden las fotos |
| terminal | la ventanilla donde se le escriben órdenes a la computadora en vez de hacer clic |
